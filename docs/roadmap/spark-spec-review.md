# Spark spec: citation and safety review (2026-09-02)

**Verdict:** Not ready to implement as written. The catalog is unusually well sourced for a community-knowledge spec and the wizard's memory arithmetic checks out (all W, KV-per-token and fit sums verified), but three structural defects would produce false alarms on a healthy DGX Spark: (1) UnifiedMemory/OnPackage are only set by detection row 5, so on stock DGX OS (row 4 matches first) the existing pcie-width-reduced rule WARNs on the misreported 'GEN 1@ 1x' link; (2) unified-memory-swap-in-use WARNs on any byte of swap and then advises 'swapoff -a' at the moment it is most dangerous; (3) dgx-spark-foreign-driver-packages CRITs on 'nvidia-dkms-*', which Ubuntu's driver metapackage may pull in legitimately, and then suggests a reimage. Detection also misclassifies an RTX Spark running Linux as dgx-spark (compute_cap 12.1 + [N/A] is tested before the 2e03/2e06 PCI IDs), and rule platform names (gh200, generic-arm64) do not match the detector's class names (grace-hopper, arm64-dgpu). Jetson and GH200 are otherwise correctly separated (Jetson tested first; GH200 requires numeric memory and CC 9.x/10.x), and generic aarch64 dGPU servers cannot reach the dgx-spark rows. The decode-throughput worked examples ignore the KV term their own formula includes (8B BF16 at 32K is 13.4 tok/s, not 17), and the nvsmi-expected evidence text mis-derives the pool (119.2 GiB minus a reserve cannot equal the measured 119.7 GiB). Roughly fifteen next steps perform driver, firmware, kernel, swap, systemd, firewall or Secure Boot changes without an advisory/reversibility marker; the fieldiag step omits the Secure Boot requirement and 'snap remove docker' / 'reimage' omit data-loss warnings. Windows-on-Arm content is mostly hedged, but GB20B-as-N1X, the WDDM 32.0 prefix, the Insider 29648 carve-out, CUDA-in-WSL2 on Arm and the torch-wheel claim are asserted beyond the cited sources. Fix the five high items and add an impact/advisory field to the rule schema before merging the catalog.

## Issues

- **[high] Spec 3.1 decision table rows 4-5 vs 5.1 suppressions; RULES platforms field**: Row 4 (/etc/dgx-release) sets Class=dgx-spark but not UnifiedMemory/OnPackage; only row 5 sets them, and the table says 'first match wins'. On every stock DGX OS box row 4 matches first, so PCIeInfo.OnPackage stays false and the existing pcie-width-reduced rule (internal/analyzer/analyzer.go ~line 678, fires on width alone, no load gate) WARNs on the misreported 'GEN 1@ 1x' link of a healthy Spark. Same for the summary VRAM line and PCIe: n/a text.
  - Fix: Set UnifiedMemory=true and OnPackage=true whenever Class is dgx-spark or rtx-spark, independent of which row matched; drop 'later rows refine' and instead state that class-derived flags are applied after classification. Add the gb10 sim assertion that report.pcie.on_package == true and that pcie-width-reduced is absent (already listed) with a fixture that includes 'GEN 1@ 1x'.
- **[high] RULES platforms values vs spec 3.1 class names**: Rules use platforms 'gh200' (grace-hopper-detected) and 'generic-arm64' (arm64-cuda12-wheel-on-cuda13, arm64-flash-attn-no-wheel, arm64-container-amd64-image, docker-snap-gpu-blocked, onnxruntime-cuda-provider-missing) but the detector only ever emits 'grace-hopper' and 'arm64-dgpu'. Those rules would never fire (or fire everywhere, depending on how an unknown platform is treated). knowledge/rules.json currently has no 'platforms' key at all, so TestRulesJSON_MatchesAnalyzer will not catch it.
  - Fix: Normalise to the spec class names (grace-hopper, arm64-dgpu) in every rule; add a test that every platforms[] entry is in the closed set {dgx-spark, rtx-spark, jetson, grace-hopper, arm64-dgpu, all}.
- **[high] Spec 3.1 row 5 vs row 7 ordering**: Row 5's third alternative (compute_cap 12.1 AND memory.total [N/A]) matches an RTX Spark N1X running Linux (also CC 12.1, also [N/A]) before row 7 checks lspci 10de:2e03/2e06, so N1X-on-Linux is classified dgx-spark and receives DGX OS / OTA / CX-7 rules.
  - Fix: Evaluate PCI-ID rows (2e12, 2e03, 2e06) before the compute_cap heuristic, or make the compute_cap+[N/A] fallback only set UnifiedMemory (Class stays unknown) rather than asserting dgx-spark.
- **[high] RULES unified-memory-swap-in-use (trigger and next_steps)**: Trigger is any swap used (>0 bytes) while utilization.gpu > 0. DGX OS ships a swapfile and Linux routinely pages a few hundred MB of cold pages, so a healthy Spark WARNs. Next step 'sudo swapoff -a' is exactly wrong at the moment the rule fires: with 6-13 GiB swapped it either fails (ENOMEM) or forces OOM kills of the running model server. Editing /etc/fstab is a persistent change.
  - Fix: Threshold on swap used >= 1 GiB (or > 2% of MemTotal) or on non-zero swap-in rate from /proc/vmstat pswpin between samples; word the step 'after stopping the workload, and only on dedicated inference hosts: swapoff -a (reversible: swapon -a); persistent change to /etc/fstab is optional and must be marked as such'.
- **[high] RULES dgx-spark-foreign-driver-packages trigger**: Trigger flags any 'nvidia-dkms-*' and any driver package 'without the -0ubuntu0.24.04 suffix' as CRIT. Ubuntu's nvidia-driver-NNN-open metapackage depends on nvidia-dkms-NNN-open, so a stock DGX OS install may legitimately carry nvidia-dkms-580-open; spec 3.2 itself lists only 'nvidia-dkms-580-open-server' as wrong. Version-suffix formats also vary (0ubuntu0.24.04.1, 0ubuntu1, OEM rebuilds). High false-CRIT risk, and the next step is 'remove ... or reimage'.
  - Fix: Restrict to the exact strings in spec 3.2 (-server variants, fabricmanager, nvswitch, non-open driver, .run installer marker /usr/bin/nvidia-uninstall) until the field kit confirms dpkg -l 'nvidia-dkms*' on a stock unit; drop the suffix test or make it INFO; move reimage into an explicit 'last resort, erases all data' sentence.
- **[high] Spec 7.4 decode ceiling vs 7.5 worked examples**: The formula is tok/s <= 273e9 / (bytes_active_weights + k x context), but every worked value ignores the KV term: 273/16.06 = 17 (8B BF16), 273/8.03 = 34, 273/4.5 = 61, 273/39.5 = 6.9. With the example's own 32K context the 8B BF16 ceiling is 273e9/(16.06e9 + 131072 x 32768 = 4.3e9) = 13.4 tok/s, not 17. The examples therefore do not follow the stated formula.
  - Fix: Either label the printed number 'weights-only ceiling (zero context)' and print a second 'at requested context' ceiling, or recompute the examples with the KV term (8B: 13.4 / 22 / 31; 70B NVFP4 at 128K: 273e9/(39.5e9+43e9) = 3.3).
- **[high] RULES gb10-logless-hard-poweroff trigger**: 'reboot: Power down' is a kernel printk emitted after systemd-journald has stopped and normally never lands in the journal; 'Reached target Power-Off' is present only for systemd-initiated shutdowns. A clean shutdown's last journal line is usually 'Journal stopped' / 'Shutting down.' so the rule as written will WARN on healthy boxes after every clean poweroff; power-button holds and mains outages also match.
  - Fix: Treat 'systemd-journald: Journal stopped', 'systemd-shutdown', 'Shutting down.', 'Reached target ... Power-Off/Reboot/Halt' as clean markers; require >=2 unclean boots in N days before WARN; mention mains loss as an alternative explanation.
- **[medium] RULES unified-memory-nvsmi-expected evidence_template**: '128 GB = 119.2 GiB minus 2-4 GB display reserve' does not add up: measured MemTotal is 125,513,944 kB = 119.7 GiB, which is larger than 119.2 GiB, so the physical pool is 128 GiB (137.4 GB) with ~8.3 GiB reserved, not 128 GB decimal minus 2-4 GB.
  - Fix: Print only measured MemTotal and say 'the remainder of the 128 GiB LPDDR5X is reserved for display/firmware (2-4 GB display reserve is configurable in BIOS)'; drop the 119.2 arithmetic.
- **[medium] Spec 7.5 header (64 GB tier 57.7 GiB) and column mixing**: 57.7 GiB is marked unconfirmed but has no derivation: proportional reserve gives 59.9 GiB, constant 8.3 GiB reserve gives 55.7 GiB. The 64 GB column silently uses F = 10 GiB (Windows) while the 128 GB column uses F = 8 GiB (Linux), and llama.cpp CUDA on Windows Arm64 (CUDA 13.4 DP) is itself unverified.
  - Fix: State the assumption explicitly ('64 GB N1X, Windows, F = 10 GiB, visible pool assumed 57.7 GiB pending measurement') and have llm-plan always use measured TotalVisibleMemorySize rather than a tier table.
- **[medium] Spec 7.4 OS floor F vs RULES unified-memory-pressure thresholds**: The wizard declares a plan 'fits' with F = 8 GiB headroom, but the analyzer WARNs at MemAvailable < 16 GiB and CRITs < 8 GiB with a GPU process. A plan the tool itself produced will therefore trigger a WARN in run, and any tight-but-valid plan a CRIT.
  - Fix: Align: WARN < 8 GiB or PSI full avg10 > 0.1, CRIT < 4 GiB or PSI full > 1.0; or raise the wizard floor to 16 GiB. Note in the rule that vLLM pre-allocation intentionally drives MemAvailable low.
- **[medium] RULES dgx-spark-ota-outdated vs cx7-not-enumerated next_steps**: ota-outdated WARNs when kernel < 6.17; cx7-not-enumerated tells users to pin linux-image-6.14.0-1015-nvidia. Following one rule's advice triggers the other.
  - Fix: Have cx7-not-enumerated recommend the fixed 6.17 kernel (>= 6.17.0-1031 per spec 2.1) and only mention the 6.14 pin as a stop-gap; suppress ota-outdated's kernel clause when cx7-not-enumerated's regression variant fired.
- **[medium] RULES dgx-spark-firmware-behind trigger**: Compares EC/SoC/PD versions against Founders Edition values while spec 2.1 says OEM units (ASUS, HP, Lenovo, Dell, MSI, Acer, Gigabyte) run their own firmware tracks. Healthy OEM units will WARN. The 'pre-production 5.36_0ACUM018' claim is unsourced and contradicts row 6 which lists 018 as a normal FE BIOS. Also fwupdmgr prints formatted versions (3.5.8), not the 0x hex, so hex comparison is not what the collector will see.
  - Fix: Gate FE thresholds on Vendor == NVIDIA; for OEMs only report pending capsules from fwupdmgr; parse and compare dotted versions; remove or source the 'pre-production' wording.
- **[medium] RULES gb10-pd-power-wedge severity**: CRIT from a single nvidia-smi snapshot (util >= 90, SM < 1400, < 40 W, no reasons). A brief DVFS transition or a light memory-bound kernel can satisfy this for one sample. S46/S47 are one forum thread and one community repo.
  - Fix: Require the signature to persist across all thermal samples of the run (collector already samples multiple times) or demote to WARN on a single sample; state 'community-observed signature, confirmed by NVIDIA support in S46' explicitly.
- **[medium] RULES dgx-spark-driver-too-old evidence_template**: 'signature: ~5 W, 0% util, power limit N/A' lists power limit N/A as a symptom, but the spec itself says power limit is always N/A on GB10; users on the correct driver will read this as confirming a fault.
  - Fix: Remove 'power limit N/A' from the signature; keep ~5 W and 0% util under load.
- **[medium] RULES dgx-spark-cublas-batch-bug vs spec 2.1**: INFO fires on every unit running the official 580.159.03 stack and asserts 580.173.02 'fixed' the bug, while spec 2.1 says researchers disagree whether 580.173.02 is official and that pulling it via apt bricked OTA2607 boxes (dgx-spark-gsp-init-failure). Same fact stated with opposite confidence.
  - Fix: Fire only on the CUDNN_FE 11 / CUBLAS 14 log strings (WARN); drop the version-only INFO variant until 580.173.02 ships in an OTA; word evidence 'reported fixed in 580.173.02 (forum report S41, not yet in an OTA)'.
- **[medium] RULES dgx-spark-suspend-failure trigger**: Matches on 'nv.c:4784', a source line number that changes with every driver build; the rule will silently stop matching on the next driver.
  - Fix: Match on 'nv_set_system_power_state' and 'WARNING: ... nvidia/nv.c' without the line number.
- **[medium] RULES arm64-cuda12-wheel-on-cuda13 severity/trigger**: CRIT on a mere +cu12x wheel tag. cu12x wheels bundle their own CUDA 12 runtime via nvidia-*-cu12 pip packages and are driver-compatible with R580; the concrete breakage on GB10 is the missing sm_121 kernels or a system-lib import error, which are already covered by the import-error string and sm121-kernel-missing. The single source (S33) is a personal setup repo.
  - Fix: CRIT only when the libcudart.so.12/libnvrtc.so.12 import error is observed; WARN for the tag alone with wording 'may lack sm_121 kernels; verify torch.cuda.is_available() and a matmul'.
- **[medium] RULES dgx-spark-detected / spec 3.1 row 5, PCI ID 10de:2e12**: The GB10 PCI device ID 10de:2e12 and BDF 000f:01:00.0 anchor the whole hardware-level detection but no source is attached to row 5 (dgx-spark-detected cites only S23/S4). If the ID is wrong, detection falls back to the nvidia-smi name and fails when the driver is dead, defeating the gsp-init-failure rule.
  - Fix: Cite an lspci -nn capture (S6/S7 or field kit) for 2e12; add it to the section 12 field-kit must-capture list explicitly (lspci -nn -d 10de:).
- **[medium] Spec 3.1 row 3 / Jetson Thor fallback**: A Thor (or any future iGPU) booted without /etc/nv_tegra_release or a 'NVIDIA Jetson' device-tree model falls to row 9 arm64-dgpu with memory [N/A]; UnifiedMemory stays false. low-vram is safe (analyzer requires VRAMTotalMB > 0) but the summary VRAM line, PCIe rules and any future VRAM rule are not.
  - Fix: Add a platform-independent fallback: memory.total == [N/A] on any NVIDIA GPU sets GPUInfo.MemoryReporting = not-supported and PlatformInfo.UnifiedMemory = true even when Class is empty.
- **[medium] RULES rtx-spark-detected sources; spec 2.2 codename; spec 8 Insider 29648; WSL on Arm**: Windows-on-Arm claims asserted beyond sources: (a) rtx-spark-detected cites admin.pci-ids.ucw.cz which is not in section 13; (b) 'codename GB20B' for N1X is inference, since the GB20B string appears in GB10 dmesg (spec 3.2), so GB20B may be the GB10 GPU's own name; (c) 'Insider 29648 adds Reserved memory for accelerators' is uncited (S99 is a 2017 blog); (d) 'WDDM 32.0.16.1600 = 616.00' assumes a WDDM 3.2 prefix on 26H1; (e) wsl-linux-driver-installed presumes CUDA-in-WSL2 works on Windows-on-Arm with RTX Spark, which S75 does not state; (f) 'no win_arm64 torch wheels exist (S26)' cites the CUDA release notes, which say nothing about torch; (g) 'RTX Spark ships 26H1 (28000)' needs S27 or a Microsoft source.
  - Fix: Add the pci-ids URL to section 13 or cite S25; mark GB20B 'internal name seen in R580 logs, mapping to N1X unconfirmed'; cite the Insider blog or drop; mark the WDDM prefix as 'expected' and match on the trailing 16.1600 only; word the WSL rule 'if WSL2 GPU passthrough is offered on Arm (unconfirmed)'; cite pytorch.org/get-started for the wheel matrix; cite S27 for 26H1.
- **[medium] RULES rtx-spark-linux-unsupported evidence_template**: 'NVIDIA has announced no Linux support' reads as an announcement that there is no support; S76 (Phoronix) reports the absence of an announcement.
  - Fix: Reword: 'NVIDIA has not announced Linux support for RTX Spark as of {date}'.
- **[low] Spec 3.1 row 10 DGXKernel**: Canonical's linux-nvidia flavour also ships on GH200 and x86 DGX systems, so 'DGXKernel' is misnamed and is set true on a grace-hopper class host; the -64k and other flavours (6.x.0-NNNN-nvidia-64k) do not match the regex.

## Next steps that need an advisory / reversibility marker

- unified-memory-swap-in-use: 'sudo swapoff -a' while swap is heavily used can fail or trigger OOM kills of the running workload; commenting swap out of /etc/fstab is a persistent change. Not marked advisory/reversible.
- dgx-spark-gsp-init-failure: 'apt dist-upgrade + fwupdmgr upgrade + reboot', 'downgrade to the paired driver', 'apt-mark hold' are driver reinstall and firmware operations; firmware flashes are not reversible; none is marked advisory.
- dgx-spark-driver-too-old and dgx-spark-foreign-driver-packages: 'reimage' erases all user data; 'Remove foreign packages and reinstall the image driver set' is a driver reinstall; neither carries a data-loss or advisory marker.
- dgx-spark-ota-torn: 'sudo apt install nvidia-firmware-580-<expected-version> and reboot' changes the GSP firmware package; not marked advisory.
- dgx-spark-driver-branch-unsupported: 'Return to the OTA-paired 580.x' is a driver downgrade; not marked.
- dgx-spark-non-nvidia-kernel: 'sudo apt install linux-nvidia-hwe-24.04' installs a kernel; not marked.
- gb10-logless-hard-poweroff: partnerdiag --field requires Secure Boot disabled (spec 2.1/S16) but the step does not say so, nor to re-enable it; 'sudo init 3' kills the graphical session; 'nvidia-smi -lgc 300,2200' is correctly marked manual with '-rgc' revert, but should add that it costs performance and does not persist across reboot.
- dgx-spark-firmware-behind and gb10-pd-power-wedge: 'apply via your vendor channel, then cold power-cycle' is a firmware update (irreversible); get-upgrades is correctly marked read-only but the apply step is not marked advisory.
- dgx-spark-suspend-failure: 'systemctl mask sleep.target suspend.target' and the gdm gsettings change are persistent system-configuration changes; add 'revert with systemctl unmask' and mark advisory.
- docker-snap-gpu-blocked: 'sudo snap remove docker' deletes the snap's containers, images and volumes; must warn about data loss and suggest 'snap save' or exporting first.
- docker-cdi-spec-missing: 'systemctl restart docker' stops every running container unless live-restore is on; mark.
- cx7-twin-link-mismatch: 'sudo rm -f /etc/nvidia/cx7-hotplug-enabled on both nodes and reboot' deletes an NVIDIA-managed file on two machines; state how to restore it (touch the file) and that it is a workaround from S63 (community), not NVIDIA guidance.
- cx7-not-enumerated: pinning linux-image-6.14.0-1015-nvidia is a kernel downgrade that conflicts with dgx-spark-ota-outdated; mark advisory.
- cx7-up-no-ip and cx7-firewall-blocks-cluster: writing /etc/netplan/40-cx7.yaml and 'ufw allow from <subnet>/24' are persistent network/security changes; mark advisory and reversible (netplan file removal, ufw delete).
- unified-memory-pressure / unified-memory-page-cache-hold: 'echo 3 > /proc/sys/vm/drop_caches' is harmless but root-only and momentarily degrades I/O; mark as optional.
- gb10-clock-cap-active: 'sudo nvidia-smi -rgc' removes a cap the user or a service set deliberately; word 'only if you set it and no longer want it'.
- Recommendation: add an 'impact' field to every rule (none | reversible | persistent | irreversible | data-loss) and have the text renderer prefix next steps with 'Advisory:' plus the revert command; the spec's section 1 'read-only' claim covers NVCheckup's own behaviour but not the advice it prints.

## Re-check of v2 (2026-09-02) and v2.1 fixes

The re-check found no remaining high issue; the five v1 highs, the arithmetic and all 127 source ids were confirmed. Two medium and six low items were fixed in v2.1: the platform-detection placement was split into `DetectPlatform` (phase 1, files only) and `ApplyPlatformFlags` (after GPU/PCIe collection); the advisory marker is defined as the word `Advisory` at the start of a step and the eight `Advisory (...)` variants were normalised to `Advisory: (...)`; `unified-memory-oom-events` and `dgx-spark-cublas-batch-bug` are `irreversible` (their step is a non-rollbackable OTA); four package/sysctl steps gained the Advisory prefix and the cuDNN step a revert; the 2e12 lspci capture is attributed to S23/S12; the RTX Spark developer-preview trigger matches only the trailing `16.1600`; the firmware version decoding is stated as major(8).minor(16).patch(8) pending an fwupdmgr capture.
