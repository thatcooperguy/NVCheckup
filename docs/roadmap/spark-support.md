# NVCheckup on DGX Spark, RTX Spark and NVIDIA Arm unified-memory platforms

Status: specification v2, 2026-09-02 (replaces the research roadmap; the v1 citation/safety review is applied). Ten research passes feed it; disagreements and uncertainty are stated inline, and claims that rest on one report are marked `single report`, `inference` or `unconfirmed`. Sources are `[Sn]`, listed in section 13. NVCheckup itself stays read-only and no new `fix` action is proposed; the advice it prints is not read-only, so every rule carries an `impact` value and state-changing next steps are prefixed `Advisory:` with the revert command (section 5).

## 1. Goals and non-goals
Recognise the platform class (`dgx-spark` incl. OEM GB10, `rtx-spark`, `jetson`, `grace-hopper`, `arm64-dgpu`) and stop every rule that assumes discrete VRAM, a fan, a power limit or a PCIe link from firing on unified-memory GPUs. Diagnose the GB10 failure modes users hit: driver/GSP pairing, foreign driver packages, the USB-C power-delivery wedge, log-less hard power-offs, unified-memory pressure, CUDA-12 wheels on CUDA 13, missing `sm_121` kernels, ConnectX-7 mistakes. Add `nvcheckup llm-plan`. Ship `windows/arm64`. Non-goals: applying clock caps, swap or driver changes (advisory only, printed as `Advisory:` steps with the revert command); load or network tests inside `run`.

### 2.2 RTX Spark (N1X, Windows on Arm)
Announced 2026-05-31 (S27); devices fall 2026 (ASUS ProArt P16/P14, Dell XPS 16, HP OmniBook X 14/Ultra 16, Lenovo Yoga Pro 9n, Surface Laptop Ultra, Surface RTX Spark Dev Box, MSI Prestige N16 Flip). 20-core Grace CPU, Blackwell RTX GPU 6,144 (PCI `10DE:2E03`) or 5,120 cores (`10DE:2E06`); the pci-ids registry (S50) files both as `GB20B [RTX Spark N1X ...]`, but the same `GB20B` token appears in GB10 R580 GSP logs (3.2, S12), so it may be a die name shared with GB10 - the GB20B-to-N1X mapping is an inference. Up to 128 GB unified LPDDR5X (ASUS ProArt P16: 24/32/48/64/128 GB per S117; other OEMs say only "up to 128 GB"); 45-80 W per press aggregates (S103); the Surface RTX Spark Dev Box is 128 GB with a 100 W envelope and ships WSL 2 preconfigured with GPU passthrough and CUDA (S122). First Arm64 driver 616.00 Developer Preview (2026-07-16, INF `nv_surface_woa.inf`, names `NVIDIA RTX Spark N1X (6144-core Blackwell RTX GPU)` / `(5120-core ...)`, S24 S25); its WDDM `DriverVersion` is expected to end in `16.1600` (the `32.0.` prefix, hence the full `32.0.16.1600` string, is unconfirmed). CUDA 13.4 Developer Preview is the first native Windows Arm64 toolkit (S26). Compute capability inferred 12.1 (bitsandbytes ships win_arm64 `sm121`), not published. Windows 26H1 (build 28000) is the device-scoped Arm release (S74); whether RTX Spark devices ship it is unconfirmed. The ~300 GB/s press bandwidth figure is unconfirmed (S103); the wizard uses 273. No public `nvidia-smi.exe` output exists. S24 S25 S26 S27 S50 S74 S103 S117 S122

### 2.3 Confusables
Jetson: `/etc/nv_tegra_release`, `/proc/device-tree/model` "NVIDIA Jetson ...", `nvidia-l4t-core`; **Thor (CC 11.0) ships `nvidia-smi` (OpenRM)**, so "no nvidia-smi" is no longer a Jetson test (S28). GH200/GB200/GB300: aarch64 + coherent memory but discrete HBM GPU (`NVIDIA GH200 480GB`, `97871MiB`), CC 9.0/10.x, BMC, NUMA nodes 9 / 34 (S29).

Flag rules, applied after classification and independent of the matching row:
- **A (class-derived).** `Class` in {`dgx-spark`, `rtx-spark`} sets `PlatformInfo.UnifiedMemory=true`, `GPUInfo.OnPackage=true` and `PCIeInfo.OnPackage=true` for every NVIDIA GPU; `Class=jetson` sets `UnifiedMemory=true`. This is what stops stock DGX OS (row 4) from ever reaching `pcie-width-reduced`, `low-vram` or the `VRAM:` summary line (v1 set these flags only in the hardware row, so row 4 matching first left them false).
- **B (platform-independent).** Any NVIDIA GPU whose `memory.total` is `[N/A]` (or whose table `Memory-Usage` is `Not Supported`) is unified memory / on-package: set `GPUInfo.MemoryReporting=not-supported`, `GPUInfo.OnPackage=true`, `PCIeInfo.OnPackage=true` and `PlatformInfo.UnifiedMemory=true` even when `Class` is empty (a Thor booted without `/etc/nv_tegra_release`, a future iGPU, row 9). S3 S7
- **C.** `Class=grace-hopper` (numeric memory) forces `UnifiedMemory=false` and `OnPackage=false`.

CPU model on arm64: `/proc/cpuinfo` has no `model name`; use `lscpu` `Model name:` lines (GB10: `Cortex-X925` and `Cortex-A725`, `Vendor ID: ARM`, `Stepping: r0p1`, `CPU(s): 20`) or MIDR (`CPU implementer: 0x41`, `CPU part: 0xd85`=X925, `0xd87`=A725, `0xd4f`=Neoverse V2). S1 S29

### 3.3 Unified-memory arithmetic (NVIDIA guidance)
`allocatable = MemAvailable + SwapFree`; if `HugePages_Total != 0` then `allocatable = HugePages_Free * Hugepagesize` and swap counts 0. Never use nvidia-smi memory, `cudaMemGetInfo` or `MemFree` as headroom. S3

## 5. Analyzer rule catalog
The machine-readable catalog (`rules`; merge into `knowledge/rules.json` with `modes`, `platforms` and `impact`) is authoritative for triggers, evidence templates, impact values and next steps. Every rule carries `impact` (`none` | `reversible` | `persistent` | `irreversible` | `data-loss`), the most invasive of its next steps; `pkg/types.Finding` gains `Impact string json:"impact,omitempty"`. Next steps that change driver, firmware, kernel, swap, systemd, firewall, Secure Boot, snap or netplan state start with the word `Advisory` (renderers and the knowledge test match the regex ^Advisory followed by a word boundary, so `Advisory:` and `Advisory: (data loss)` both qualify) and carry the exact revert command or an explicit data-loss warning; the text and markdown renderers print `Advisory:` steps distinctly (own marker, impact shown in the finding header) and read-only steps always come first. `platforms[]` values are the detector's class names, the closed set {`dgx-spark`, `rtx-spark`, `jetson`, `grace-hopper`, `arm64-dgpu`, `all`}; a knowledge test rejects anything else. `analyzerSourceIDs` in `analyzer_knowledge_test.go` must scan every non-test `.go` file of the package so rules can live in `analyzer_spark.go`, `analyzer_cluster.go`, `analyzer_woa.go`. `dgx-spark` covers FE and OEM GB10. Modes: platform and unified-memory rules in every mode; `sm121-*`, `arm64-*`, `docker-*`, `onnxruntime-*`, `gb10-k8s-*` in `ai`/`creator`/`full`; `cx7-*`/`nccl-*` in `ai`/`full`.

## 7. LLM optimization wizard: `nvcheckup llm-plan`
### 7.1 UX
`nvcheckup llm-plan [--model NAME | --params B --active-params B --layers N --kv-heads N --head-dim N | --hf-config config.json] [--quant bf16|fp8|q8_0|nvfp4|mxfp4|q4_k_m] [--context TOKENS] [--concurrency N] [--profile chat|agent|batch|rag] [--runtime vllm|trtllm|sglang|llamacpp|ollama|auto] [--kv-dtype auto|f16|fp8|q8_0] [--headroom-gib N] [--memory-gib N] [--json] [--out DIR]`. Without `--model` it asks doctor-style questions. It reads the platform, `/proc/meminfo` (Windows: `TotalVisibleMemorySize`/`FreePhysicalMemory`), running servers and the ecosystem probes, then prints a plan. Exit codes: 0 fits, 1 fits with warnings, 2 does not fit, 3 error. `doctor` gains one hand-off question on GB10/N1X hosts.
### 7.2 Inputs
Model shape (`knowledge/models.json` or `--hf-config`: `num_hidden_layers`, `num_key_value_heads`, `head_dim` or `hidden_size/num_attention_heads`, `num_local_experts`/`num_experts_per_tok`, `sliding_window`, `quantization_config`), total/active parameters, quant, context, concurrency, profile (agent = context x (1 + subagents); 30K-120K contexts typical, S79), runtime, measured pool (MemTotal, MemAvailable, swap), bandwidth (GB10 273 GB/s; N1X press ~300 GB/s unconfirmed, use 273).

### 7.4 Formulas
- Weights `W = P_total x b`; `b`: bf16/fp16 2.00, fp8 1.00, q8_0 1.06, nvfp4 0.5625 -> 0.56 (4-bit values + one FP8 scale per 16-weight block = 3.56x smaller than BF16 for the quantized tensors; NVIDIA's checkpoint-level '~3.3x' figure (S82) corresponds to ~0.61 B/param because embeddings, lm_head and norms stay 16-bit - the wizard uses 0.56 for the quantized body and prefers the measured checkpoint size when known), mxfp4 0.53 for expert weights (attention/embeddings bf16; prefer the measured checkpoint size, gpt-oss-120b ~61 GB), q4_k_m 0.60 (0.62 measured). S2 S82 S83
- KV per token `k = 2 x L x H_kv x d_head x bytes_kv` (f16 2, fp8/q8_0 1, q4_0 0.5); `KV = k x context x concurrency` (agent: concurrency = 1 + subagents). Hybrid Mamba models add a measured per-slot state term. S84
- Runtime reserve `R` (design choices, inference): llama.cpp/Ollama 3 GiB; vLLM 12 GiB (one report in S85 measured ~3 GB runtime + ~13 GB torch.compile/CUDA graphs; a single report (S111) saw transient kernel-init allocations up to ~50 GB on `vllm:26.07-py3`, so the wizard re-checks MemAvailable after startup); SGLang 10 GiB and TRT-LLM 10 GiB (no primary source; sized like vLLM minus the compile cache). S85 S86 S111
- OS floor `F`: 8 GiB headless DGX OS, 10 GiB with GNOME or on Windows (inference, no primary source); a community watchdog kills training jobs when MemAvailable < 16 GB (S33, one setup guide). The analyzer's `unified-memory-pressure` thresholds (WARN < 8 GiB, CRIT < 4 GiB with a GPU process) are aligned with `F` so a plan the wizard accepts does not WARN in `run`.
- Fit: `W + KV + R + F <= MemTotal` (design) and `W + KV + R <= MemAvailable_now`. Pool = MemTotal (119.7 GiB on a 128 GB unit), never "128 GB".
- vLLM `--gpu-memory-utilization u = ceil05((W + KV + R) / MemTotal)` clamped 0.30..0.85 (vLLM's Spark guidance: 0.85, `--max-num-seqs 4`; default 0.92 pre-allocates ~110 GiB). TRT-LLM `free_gpu_memory_fraction` and SGLang `--mem-fraction-static` reuse `u` (SGLang playbook default 0.75). S86 S87
- Decode ceiling, two numbers per plan: weights-only `tok/s <= 273e9 / bytes_active_weights` (zero context) and at-context `tok/s <= 273e9 / (bytes_active_weights + k x context)` for one stream; the wizard prints both, labelled, plus a 50-80% realism band on the at-context value (measured: 8B FP8 20.5 vs 34 weights-only / 22 at 32K; 70B FP8 2.7 vs 3.9 weights-only; gpt-oss-120b 42-61 measured; Nemotron 3 Super NVFP4 23-38 measured). Prefill: quote measured 2,000-8,000 tok/s. Ollama does not batch (aggregate = single stream); vLLM aggregate reaches hundreds of tok/s at c=8..256. S88 S89 S90
